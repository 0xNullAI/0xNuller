# 跨平台、多窗口 App 重构计划

状态：2026-09-29 设计与实施方案。用户进一步明确：**先判断现有代码结构能否承载新需求，只修必要部分**。本文件的信息架构和断点是验收目标，不要求重写已有页面组件或更换整套视觉。2026-09-29 曾试做导航轨布局，用户认为观感不合适，已撤回；后续 UI 变更必须针对实际页面问题单独评审。产品范围以[网站统一聊天与角色平台执行计划](companion-platform-final-plan.md)为准。本地 `develop` 已有统一登录入口的代码改动，尚未发布；原 `dev`/`main` 版本保留。

## 1. 目标和不变的边界

新版从统一登录页进入，登录后落在消息首页。AI 私聊、真人私聊、真人群聊共用会话与消息界面；发现、联系人、设备、我的围绕它组织。手机参考 QQ 的消息与联系人习惯，桌面采用简洁的列表—详情结构，平板和窄桌面随**窗口宽度**连续调整，不按“手机/电脑”硬判。Apple 的[分栏建议](https://developer.apple.com/design/human-interface-guidelines/split-views?changes=_6)、Android 的[自适应窗口指南](https://developer.android.com/develop/adaptive-apps/guides/get-started-with-adaptive-apps)与 Windows 的[列表详情模式](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/list-details)都支持这种按可用宽度决定单栏或多栏的方案。

原设备连接、协议、物理身份、权限、限额和停止链路保持；旧路径、管理页面和已保存内容保留。聊天与私人资料由服务器授权和持久化，浏览器多窗口仅缓存当前显示状态，不再各自持有一份长期聊天。Market 是角色、场景和波形的唯一卡片入口；无内置场景、多人场景或多角色 AI 编排。Avatar/AR 暂不做，头像、语音、情境图片和视频仍在当前路线。

## 2. 信息架构：五个去向，功能不再占据一级导航

| 一级去向 | 主要页面                                       | 二级内容和动作                                                    |
| -------- | ---------------------------------------------- | ----------------------------------------------------------------- |
| 消息     | 全部会话、未读、搜索、置顶；选中后进入统一聊天 | AI 私聊、真人私聊、真人群；语音/视频/工具/图片从会话内打开        |
| 联系人   | 好友、关注的人、群与邀请                       | 资料、添加、群管理、开始真人聊天；管理员入口仍只对管理员可见      |
| 发现     | Market 的浏览全部、收藏、关注作者              | 角色、场景、波形；筛选、详情、导入、创建/编辑                     |
| 设备     | 未连接入口或已连接控制台                       | 原连接、状态、归零/停止、安全上限；不另加重复“我的设备/连接”标题  |
| 我的     | 账户资料与设置列表                             | 个人/关系记忆、聊天共享与安全、通知、Credit/订单、外观、管理/关于 |

原 `/agent`、`/voice`、`/video`、`/chat`、`/control`、`/market` 等链接继续可用：URL 进入后定位到新的对应页面或能力，不因视觉改版失去功能。独立设置采用列表→二级页；角色专属记忆和权限从该聊天的详情进入，同一设置组件服务 AI 和真人作用域。Market 创建为页面式编辑器，默认只有名字、基础 Prompt、头像和预览，其余按需展开。

建议的新路径为 `/messages`、`/messages/:conversationId`、`/contacts`、`/discover`、`/devices`、`/me`、`/settings/:section` 和 `/discover/edit/:itemId`。根路径转到消息；旧路径以兼容映射进入相应能力，复制链接、刷新和前进/后退都应保持对象与页面状态。分享的公开卡链接先经过统一登录，再回原卡片；因此访客不能直接浏览卡片，公开搜索收录不作为这一版的获取入口。

## 3. 一个外壳，随窗口伸缩

以下断点是**设计起点**，实施时根据真实内容最小宽度和字体放大测试调整。窗口缩放只改呈现，不改变功能或会话身份。

| 可用宽度    | 外壳                                               | 消息/联系人/发现                                                                  |
| ----------- | -------------------------------------------------- | --------------------------------------------------------------------------------- |
| 320–599 px  | 单栏、底部五入口；聊天详情占满页面，返回回到原列表 | 一次只显示列表或详情；输入框贴安全区域，键盘弹出后仍可发送和停止                  |
| 600–899 px  | 紧凑侧栏或导航轨；一级入口仍一眼可找               | 优先列表—详情两层顺序切换；空间够时两栏并排，不挤成三栏                           |
| 900–1399 px | 窄导航轨 + 可收起会话列 + 主内容                   | 消息是列表/聊天双栏；Market 是内容网格；设置占主内容，不叠弹窗                    |
| ≥1400 px    | 可展开侧栏 + 会话列 + 宽主内容                     | 聊天内容限制可读行宽；成员/角色详情只在主动打开时作为右侧检查面板，不默认占第三栏 |

高度也要适配：短窗口把次要工具放溢出菜单，列表和正文各自滚动，标题和输入/停止操作保持可达。不要让设备条、模块按钮和筛选条层层占高。支持浏览器缩放、系统字体放大、旋转、折叠屏和桌面窗口拖动；页面局部可用 [container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_size_and_style_queries)，避免只依赖整个 viewport。

## 4. 页面与视觉规则

- **统一聊天**：一套消息气泡、时间、发送状态、附件、引用和未读；顶栏只显示对象、在线/任务状态及少量核心动作。AI 的工具证据、场景和记忆设置在详情中，语音/图片/视频放输入区的一个能力菜单，失败和实际 Credit 明确显示在消息附近。真人消息不出现 AI 专属文案。
- **联系人与群**：搜索和列表优先；详情页承载资料、共同群、权限与开聊。群成员、邀请、管理保持原后端权限，AI 仅作为明确加入且被 @ 才回复的单个参与者。
- **发现/Market**：上排“浏览全部／我的收藏／关注作者”，下排“角色／场景／波形”，创建在右端。筛选按钮展示选中数；展开后排序与有效条件清晰，一次可重置。角色详情可导入并聊天，场景详情仅导入/应用，波形归设备内容。
- **设备**：未连接时一张主要连接卡与必要说明；已连接时优先显示设备、状态、通道和停止。设备详情、安全设置为二级页；停止入口不被菜单、滚动或登录态遮住。连接逻辑完全沿用原 owner。
- **我的/设置**：标准分组列表，不做密集下拉和账号弹窗。第一屏只显示账户摘要及少量分组；每个二级页一个清楚的返回路径。个人记忆、聊天级共享、安全默认值和 Credit 分开，措辞按用户是否授权呈现。

使用一套系统字体栈、固定的字号梯度（辅助 12、正文 14–16、标题 20–24 px）、统一行高与间距刻度，优先删重复句而不是把所有字缩小。颜色承担层级，状态同时有文字或图标；触控目标和键盘焦点明确。浅色/深色同一信息结构，图像和表情不替代可访问名称。Windows 的[设计指南](https://learn.microsoft.com/en-us/windows/apps/design/guidelines-overview)特别强调导航、文字与布局的一致性；本方案借鉴原则，不复制任一平台的整套外观。

## 5. 多窗口与跨端的状态模型

1. **URL 是定位**：`/messages/:conversationId`、角色/场景详情、编辑器和设置二级页可直接打开、刷新、浏览器前进/后退；登录后返回原 URL。当前选中会话不只藏在某个窗口的 React 状态中。
2. **服务器是权威**：消息有服务器序号、幂等发送 ID、未读游标与任务 ID；两个窗口同时发消息、撤回、充值或打开同一卡不会互相覆盖或重复扣费。窗口重连按游标补齐，草稿和卡片编辑使用版本冲突提示。
3. **跨窗口只传失效通知**：同源窗口可用 [BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API)通知“新消息/退出/卡片变更”，接收方仍从服务器按权限重读，不广播消息正文、记忆或凭据。跨浏览器和跨设备完全依赖服务器同步。
4. **一次只有一个实时操作 owner**：同一账户的语音/摄像头会话与本机设备控制要有可见的活动窗口和接管/拒绝状态；锁和租约用于协调，**最终设备执行仍在原本机安全 owner 重验**。可用 [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)协调同源窗口，但浏览器不支持或锁失效时，新输出必须拒绝，不能靠 UI 约定避免双控。
5. **停止与退出**：每个仍连接设备的窗口保留本机归零/停止入口；另一窗口退出账户后，当前窗口收到失效通知并重新验证服务器会话，撤销新任务和权限。后台窗口暂停无用轮询；正在使用的语音/设备不会因页面隐藏而被误判为安全可继续，需明确前后台策略。

“多窗口兼容”第一阶段指浏览器多标签、独立窗口、桌面 App 多窗口与手机分屏/旋转都正常工作；不先增加复杂的任意弹出小窗系统。确有使用场景时，再给聊天详情和编辑器添加“在新窗口打开”，复用相同 URL 和上述并发契约。

工程上维持一个路由/history owner、一个全局覆盖层 owner 和一个设备安全锚点。外壳只负责登录、导航、窗口布局与安全状态；消息、Market、设备、设置分别拥有自己的页面内容与服务适配。共享列表—详情框架、输入区和状态组件，不在 Agent、Chat、Voice 页面各复制一套顶栏、账户入口或登录页。现有按需加载模块可分批接入这一外壳，不需要一次搬迁全部后端。

## 6. 功能实施顺序与并行分工

| 阶段              | UI/外壳                                                              | 后端与数据                                                   | Agent、媒体与设备                                 | 验收                                                     |
| ----------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------- | -------------------------------------------------------- |
| A. 契约和原型     | 页面地图、三种窗口线框、交互/字号令牌；统一登录和路由回跳            | 会话、卡片实体、权限、消息与费用 ID 契约                     | 工具结果/场景组合/设备 owner 边界                 | 可点击原型走通登录→发现→导入→聊天→设置；旧路径和设备不丢 |
| B. 外壳与核心页面 | 消息、联系人、发现、设备、我的在所有宽度落地；删重复文案和多层工具栏 | 服务器消息、跨端游标、旧本地历史迁移；Market kind 与在线编辑 | Agent 接统一会话；工具真实结果先可见              | 两窗口/两终端续聊，未登录只见统一登录，安全停止可达      |
| C. 关系和社群     | 聊天详情、个人/会话记忆设置、真人群与通知                            | 分层记忆、关系历史、主动任务、群成员权限                     | 工具多步执行、单 AI @ 与记忆隔离                  | 纠错/删除不复活；群与私聊不串记忆；主动聊天可取消        |
| D. 多模态与商业化 | 语音/视频/生成结果回消息时间线，Credit/订单状态一致                  | 统一代理、预留/结算/失败释放、正式支付对账                   | Voice/Video 与角色+场景共用上下文，媒体任务可恢复 | 断线/重试不伪造结果或重复扣费；真实服务商和支付沙箱验证  |
| E. 社区与质量     | 作者关注、推荐与内容运营、细节打磨                                   | 事件统计、审核、作者 Credit 奖励                             | 记忆质量、成本/延迟与更多授权工具评测             | 端到端质量、可访问性、隐私和成本达标；无创作者提现       |

前两阶段可让 UI、后端、Agent 分工并行，但先统一接口样例、加载/失败/空态和错误码；每阶段有一个整链集成分支验收，不把各模块孤立完成算成上线。现有管理员页、旧链接和设备连接路径不做大规模迁移。Avatar/AR 在这些阶段之外。

## 7. 设计和发布门槛

先用现有页面评审 390px 手机、约 800px 平板/窄窗、1440px 宽窗的登录、空消息、AI/真人/群聊天、发现筛选、未连接/已连接设备、我的设置和角色编辑。记录具体拥挤、重复或断裂处，优先修改原组件和共享样式；只有现有组件确实无法表达统一会话或权限边界时才拆分。测试矩阵至少覆盖 320、390、600、768、1024、1440、1920px 宽度以及短窗口；Chrome/Edge/Safari、Android/iOS 浏览器和桌面壳按实际支持范围检查。还需键盘、触摸、200% 字体/缩放、系统安全区域、暗色模式与低速网络。

重点回归两窗口同账号、两窗口不同账号、登录/退出、同一聊天并发发送、同一卡并发编辑、语音占用、设备连接和停止、失焦/恢复、断网/重连、Credit 幂等，以及 Android 上 AI 主动消息、私聊、群聊的推送落点和账号切换隔离。点推送在现有 App 内导航，不能重载并断开设备。原生产版本继续由 `dev`/`main` 保留；新版仅在 `develop` 完成上述门槛后按仓库发布流程推进，生产迁移另做备份、预发演练和核对。当前计划本身不批准部署或真实设备操作。
